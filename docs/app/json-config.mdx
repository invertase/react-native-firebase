## Prerequisites

- A React Native or Expo project with `@react-native-firebase/app` installed per [Getting Started](/).
- Native config in place when you rely on platform SDKs: Android `google-services.json`, iOS `GoogleService-Info.plist`, or Expo `googleServicesFile` fields.

You configure installed React Native Firebase modules by creating `firebase.json` at the **project root** (next to `package.json`).

Order:

1. Create or edit `<project-root>/firebase.json` (schema snippet below). Apply it before the next native build or Expo prebuild.
2. Rebuild the native app (or re-run Expo prebuild / EAS Build) so native code picks up the constants.

All settings live under the top-level `react-native` key:

```json
// <project-root>/firebase.json
{
  "react-native": {
    "...": "..."
  }
}
```

## JSON Schema

Add the [Config Schema](https://github.com/invertase/react-native-firebase/blob/main/packages/app/firebase-schema.json) to your `firebase.json` file to enable editor IntelliSense. The `$schema` path is relative to the project root after `@react-native-firebase/app` is installed:

```json
{
  "$schema": "./node_modules/@react-native-firebase/app/firebase-schema.json",
  "react-native": {}
}
```

All keys go inside the `react-native` object. A file without a `react-native` key is treated as an empty configuration and every key keeps its default. The schema file lists each key's type and description.

## Keys

The schema defines 35 keys. Six apply to the app module or to several modules, and are described in the first table. The remaining 29 belong to one module each and are listed by module in the second table.

### App and cross-module keys

{/* prettier-ignore */}
| Key | Type | Platform | Default | Runtime override |
| --- | --- | --- | --- | --- |
| `app_data_collection_default_enabled` | boolean | Android, iOS | `true` when unset | `automaticDataCollectionEnabled` on a `FirebaseApp` and in the `initializeApp` config. Module-specific keys and APIs take precedence for their module. |
| `app_log_level` | string: `error`, `warn`, `info`, `debug` | iOS only | Not set, so the Firebase iOS SDK default level applies | `setLogLevel` |
| `android_task_executor_maximum_pool_size` | number | Android only | `1` | None |
| `android_task_executor_keep_alive_seconds` | number | Android only | `3` | None |
| `android_background_activity_names` | array of strings | Android only | None | None |
| `android_bypass_emulator_url_remap` | boolean | Android only | `false` | None |

- `app_data_collection_default_enabled`: whether automatic data collection is on for all products unless a product-specific setting overrides it. Set it to `false` for opt-in-first flows such as GDPR consent, then turn collection on after consent. When the key is `false`, modules whose own collection key is unset start with collection off. It is applied at build time (Android manifest placeholder, iOS `Info.plist` entry `FirebaseDataCollectionDefaultEnabled`).
- `app_log_level`: read when the app module loads on iOS and ignored on Android. `setLogLevel` and `onLog` have their own scope, described in [Logging](/app/usage#logging).
- `android_task_executor_maximum_pool_size` and `android_task_executor_keep_alive_seconds`: tune the thread pool that Android uses for module work. See [Android Performance](/#android-performance) for the effect of each value.
- `android_background_activity_names`: short class names (the value of `getShortClassName()`) of activities that run outside React Native. They are ignored when React Native Firebase decides whether the app is in the foreground before it calls JavaScript background handlers.
- `android_bypass_emulator_url_remap`: on Android, `useEmulator` for Auth, Database, Firestore, Functions and Storage maps `localhost` and `127.0.0.1` to `10.0.2.2`. Set this key to `true` to keep the host you pass.

Example `firebase.json` that turns off default data collection, sets the iOS log level and raises the Android executor pool size:

```json
{
  "$schema": "./node_modules/@react-native-firebase/app/firebase-schema.json",
  "react-native": {
    "app_data_collection_default_enabled": false,
    "app_log_level": "debug",
    "android_task_executor_maximum_pool_size": 10
  }
}
```

## File lookup and parsing

Each native build step finds `firebase.json` on its own. A file in the project root is found by all of them:

- Android (Gradle): checks the parent directory of the `android/` folder (the project root), then up to three directories above it.
- iOS (CocoaPods): checks up to five directories above the `@react-native-firebase/app` package.
- iOS (Xcode build script): searches the project root first and, only if it finds nothing, the parent of the project root. In each of those two directories it matches a `firebase.json` that sits directly in the directory or directly inside a folder in that directory. The first match found wins, and the order in which those folders are visited is not specified.

Because of the Xcode build script search, keep a single `firebase.json` at the project root. A second `firebase.json` inside a nested folder, for example a Firebase CLI project folder, can be picked instead of the root file.

Keep the file strict JSON: no comments and no trailing commas. A parse failure behaves differently on each step:

- Android: the build logs a warning that `firebase.json` failed to parse and continues with an empty configuration.
- iOS, `pod install`: prints a warning and continues with defaults.
- iOS, Xcode build script: if the file cannot be parsed, the build fails with `Failed to parse firebase.json, check for syntax errors.` The script also needs `python3` on the path once the file has a `react-native` key. If the Python step that bakes the config into `Info.plist` fails, the baked config falls back to `{}`. At runtime, iOS also falls back to `{}` when the baked value cannot be decoded.

If no `firebase.json` is found, the iOS build prints a warning and continues with defaults. A CI build that hangs at the Core Configuration step may be fixed by creating the file with an empty `react-native` object, as described in [FAQs and Tips](/faqs-and-tips).

## Reading config at runtime

After a native rebuild, call `jsonGetAll` to read the constants that were baked in from `firebase.json`. This is a React Native Firebase helper (no firebase-js-sdk modular equivalent). On [Other platforms](/platforms#other-platforms) it resolves to an empty object:

```js
import { jsonGetAll } from '@react-native-firebase/app';

async function logFirebaseJson() {
  const constants = await jsonGetAll();
  console.log('firebase.json constants:', constants);
}
```

## Schema Reference

The table below mirrors the descriptions in [`firebase-schema.json`](https://github.com/invertase/react-native-firebase/blob/main/packages/app/firebase-schema.json); when the schema changes, update it first and keep this table in sync.

Every property below is optional. Values are read when the app is built or launched; a property can only be changed later in JavaScript where its description says so. The **Changeable via JS** column marks the properties that also expose a JavaScript override at runtime (✅); the rest are read once, at build or app launch.
